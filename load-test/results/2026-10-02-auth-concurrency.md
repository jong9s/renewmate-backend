# 동시 회원가입·로그인 k6 시험 (2026-10-02)

## 목적

가입자 수가 증가할 때 인증 API가 여러 사용자의 동시 요청을 어떻게 처리하는지 확인했다. 기존의 구독 조회 시험은 로그인과 회원가입의 동시 부하를 검증하지 않았다.

## 시험 조건

- 대상: AWS EC2 `t3.micro`에서 Spring Boot 앱과 MySQL이 함께 실행되는 서비스.
- 부하 생성: Windows 로컬 PC의 k6 v2.2.0. 서버에 k6를 설치하지 않았다.
- 스크립트: [`../scenarios/auth-concurrency.js`](../scenarios/auth-concurrency.js).
- 실행 방식: `per-vu-iterations`로 VU마다 요청을 1회씩 시작하는 짧은 동시 요청 시험. `maxDuration`은 2분.
- 10명 사전 시험 후 100명 시험을 각각 실행했다. 회원가입은 VU별 고유 이메일, 같은 암호를 사용했다. 인증 정보는 결과 파일에 저장하지 않았다.
- 100명 시험 계정 접두사: `loadtest-auth100-20261002-2131-<VU>@example.com`.
- 회원가입(`/api/auth/signup`, 기대 201) → 같은 계정들로 로그인(`/api/auth/login`, 기대 200 및 토큰) → 로그인 후 회원탈퇴(`/api/users/me`, 기대 204) 순서로 실행했다. 정리 단계도 k6로 실행했다.
- 이번 인증 시험에서는 서버 CPU·메모리·CPU 크레딧을 새로 수집하지 않았다. 따라서 지연 증가의 서버 측 원인은 아직 확인되지 않았다.

## 결과

| 단계 | VU | 성공/시도 | 응답 평균 | 응답 p95 | 실행 전체 소요 | 원본 요약 |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| 회원가입 사전 시험 | 10 | 10/10 | 1.073초 | 1.074초 | 약 1.10초 | [JSON](auth10-signup.json) |
| 로그인 사전 시험 | 10 | 10/10 | 0.478초 | 0.492초 | 약 0.53초 | [JSON](auth10-login.json) |
| 사전 시험 계정 삭제 | 10 | 10/10 | - | - | 약 1.95초 | [JSON](auth10-cleanup.json) |
| 동시 회원가입 | 100 | 100/100 | 2.816초 | 4.886초 | 약 5.00초 | [JSON](auth100-signup.json) |
| 동시 로그인 | 100 | 100/100 | 4.678초 | 4.910초 | 약 4.96초 | [JSON](auth100-login.json) |
| 시험 계정 삭제 | 100 | 100/100 | - | - | 약 21.15초 | [JSON](auth100-cleanup.json) |

정리 단계의 성공 수는 204 회원탈퇴 응답 수다. 정리 단계에는 로그인 요청도 포함되어 있어 HTTP 요청 수는 10명에서 20회, 100명에서 200회다. 100명 시험은 회원가입 100개와 로그인 100개에서 HTTP 오류 0건, k6 검증 실패 0건이었다.

## 해석

- 100개의 요청을 거의 동시에 시작했지만, 서버가 처리하는 동안 완료된 속도는 회원가입 약 20 RPS, 로그인 약 20 RPS였다. `100 VU = 100 RPS`가 아니다.
- 10명에서 100명으로 늘릴 때 성공률은 유지됐으나 p95는 회원가입 약 1.07초 → 4.89초, 로그인 약 0.49초 → 4.91초로 증가했다. 100명 동시 인증 시 사용자가 수 초를 기다릴 수 있다.
- 한 번의 짧은 burst 시험이다. 장시간 지속 처리량, 실패가 시작되는 지점, 서버 자원 병목은 측정하지 않았다.
- 모든 계정은 서로 다른 이메일이지만 같은 암호를 사용했다. DB 계정 수가 5,000명인 상태에서 시험하지 않았다.
- 출발 서비스 가정의 피크 15 RPS와 이 시험은 목적이 다르다. 피크 시험은 지속 요청률, 이 시험은 순간 동시 인증 요청을 확인한다. 실제 피크 로그인·가입 비율은 운영 데이터가 없어 미정이다.

## 재현 및 주의

실행에 사용한 코드는 [`../scenarios/auth-concurrency.js`](../scenarios/auth-concurrency.js)에 있다. 다음에 비교하려면 동일한 서버 사양, 계정 수, 요청 수, 워밍업 조건으로 최소 여러 차례 반복하고, 서버 CPU·메모리·스왑 입출력·DB 상태를 동시에 수집해야 한다. 특히 이번 결과만으로 bcrypt, DB 또는 메모리 중 어느 것이 지연 원인인지 단정할 수 없다.
