# 동시 인증 지연 원인 분석과 개선 (2026-10-12)

## 배경

EC2 t3.micro(2 vCPU)에서 동시 회원가입·로그인 100건을 보내면 모두 성공했지만, p95가 약 4.9초였습니다 ([2026-10-02 EC2 결과](../2026-10-02-ec2/2026-10-02-auth-concurrency.md)). 동시 요청이 10명일 때와 100명일 때 모두 처리 속도가 **초당 약 20건**으로 같았습니다. 처리량에 상한이 있어 요청이 줄을 서는 모양이었습니다.

## 측정 환경

- **PC**: Intel Core Ultra 5 125H, k6 v2.2.0, MySQL 8.0.46
- **앱 CPU 고정**: 앱 JVM을 **CPU 2개로 고정**(processor affinity)해 t3.micro의 2 vCPU와 비슷하게 맞췄습니다. MySQL과 k6는 고정하지 않았습니다. EC2에서는 MySQL도 같은 2 vCPU를 나눠 쓰므로, 운영 수치는 이보다 나쁠 수 있습니다.
- **운영과 같은 JPA 설정**: `spring.jpa.open-in-view=false`, SQL 로그 끔
- **DB**: 측정마다 빈 DB를 새로 만들고 Flyway V1~V4를 적용했습니다.
- **반복**: 폭주 시나리오는 설정마다 3회씩 반복했습니다. 표의 값은 **3회의 중앙값**입니다.

## 1. 원인: BCrypt 해싱의 CPU 비용

| 측정 | 결과 |
| --- | --- |
| BCrypt(strength 10) 비교 1회 | 약 69 ms (스레드 1개) |
| 스레드 2개로 낼 수 있는 처리량 | 초당 약 30회 |
| 동시 인증 100건 (앱 CPU 2코어) | 초당 약 24~26건, p95 약 4.0 s, 앱 CPU 사용 1.8코어 |

인증 처리량이 해싱 처리량의 상한에 걸려 있고, CPU가 포화 상태입니다. 100건이 동시에 오면 마지막 요청은 100 ÷ 24 ≈ 4초를 기다립니다.

## 2. 더 큰 문제: 인증이 몰리면 다른 API까지 멈춤

`auth-burst-with-read.js`로 구독 조회를 15 RPS로 보내는 도중 로그인 또는 회원가입 100건을 한꺼번에 보냈습니다. 조회 응답 시간은 폭주 구간 안과 밖으로 나눠 기록했습니다.

| 조회 API p95 (중앙값) | 폭주 없음 | 로그인 폭주 중 | 회원가입 폭주 중 |
| --- | --- | --- | --- |
| **개선 전** | 17 ms | 114 ms (87 ms ~ 2.5 s) | **3.29 s** (3.0 ~ 3.4 s) |

- **회원가입 폭주**: `signup()`이 트랜잭션 안에서 해싱해서, 해싱하는 동안 **DB 커넥션을 붙잡았습니다**. 커넥션 풀(10개)이 고갈되자 조회 요청이 커넥션을 기다렸습니다.
- **로그인 폭주**: 해싱 스레드 수십 개가 CPU를 나눠 쓰면서 조회 요청이 CPU 차례를 기다렸습니다.

참고로 로컬 기본 설정(`open-in-view=true`)에서는 로그인도 요청이 끝날 때까지 커넥션을 쥐어서, 로그인 폭주 중 조회 p95가 약 3.3초까지 나빠졌습니다. 이 측정은 [`osiv-on/`](osiv-on/)에 따로 보관했습니다.

## 3. 개선

1. **해싱 동시 실행 제한**: `ConcurrencyLimitedPasswordEncoder`에 Spring 7의 `@ConcurrencyLimit`(한도 2, BLOCK)를 적용했습니다. 한도를 넘는 요청은 거절하지 않고 차례를 기다립니다.
2. **회원가입에서 트랜잭션 제거**: 해싱하는 동안 DB 커넥션을 쥐지 않습니다. 저장은 `save()` 한 번이라 자체 트랜잭션으로 충분합니다.
3. **해싱 강도는 유지**: strength 10 그대로입니다. 강도를 낮추면 빨라지지만 비밀번호 보안이 약해집니다.

## 4. 결과

| 조회 API p95 (중앙값, 범위) | 로그인 폭주 중 | 회원가입 폭주 중 |
| --- | --- | --- |
| 개선 전 | 114 ms (87 ms ~ 2.5 s) | 3.29 s (3.0 ~ 3.4 s) |
| 회원가입 트랜잭션 제거만 (해싱 한도 없음) | 233 ms (213 ~ 627 ms) | 316 ms (18 ms ~ 2.4 s) |
| **개선 후 (둘 다 적용)** | **20 ms** (14 ~ 192 ms) | **22 ms** (7 ~ 36 ms) |

| 인증 자체 (동시 100건) | 개선 전 | 개선 후 |
| --- | --- | --- |
| 회원가입 p95 / 처리량 | 4.03 s / 초당 24.6건 | 4.01 s / 초당 23.8건 |
| 로그인 p95 / 처리량 | 3.79 s / 초당 26.2건 | 4.17 s / 초당 23.3건 |

**해석**
- **다른 API 보호**: 인증 폭주 중 조회 p95가 회원가입 폭주 기준 **3.29 s에서 22 ms로** 줄었습니다. 두 개선을 함께 적용해야 결과가 안정적이었습니다. 트랜잭션 제거만으로는 커넥션 고갈은 사라졌지만, CPU 경합 때문에 편차가 컸습니다.
- **인증 자체는 그대로**: 인증 지연과 처리량은 변하지 않았습니다. CPU 2개로 계산할 수 있는 해싱 양이 그대로이기 때문입니다. 인스턴스 하나의 인증 처리량은 초당 약 20~25건이 한계입니다. 더 필요하면 vCPU를 늘리거나(스케일 업) 서버를 늘려야(스케일 아웃) 합니다.
- **한도를 1로 줄이면 오히려 손해**: 한도 1(개선 중 OSIV 켠 상태로 측정)은 인증 처리량이 초당 15건으로 떨어져, 대기가 길어지면서 오히려 나빠졌습니다. 그래서 한도는 vCPU 수(2)로 정했습니다.

## 5. 한계

- **로컬 재현 측정입니다.** EC2에서 다시 측정하지 않았습니다. MySQL이 고정한 CPU 밖에서 실행됐고, CPU 고정은 t3의 CPU 크레딧(버스트) 특성을 재현하지 않습니다.
- **반복 횟수가 적습니다.** 3회 반복이라 범위가 넓은 값(특히 개선 전 로그인 폭주)은 편차가 큽니다.

## 파일

- `<설정>-auth{10,100}-{signup,login}.json`: 동시 인증 (`auth-concurrency.js`)
- `<설정>-read-only.json`: 조회 15 RPS 단독, 30초 (`subscription-read.js`)
- `<설정>-read-with-{login,signup}-burst-{1,2,3}.json`: 폭주 중 조회 (`auth-burst-with-read.js`)
  - `read_during_burst`: 폭주 시작 후 8초 동안의 조회
  - `read_outside_burst`: 그 밖의 조회
  - `burst_login`: 폭주 요청 자체의 응답 시간
- `<설정>`
  - `before`: 개선 전
  - `after`: 개선 후 (한도 2)
  - `nolimit`: 회원가입 트랜잭션 제거만, 해싱 한도 200
- `osiv-on/`: 로컬 기본 설정(`open-in-view=true`)에서 측정한 첫 결과 (단일 실행)
